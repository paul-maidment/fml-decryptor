FML File Format & Encryption

Complete reference for the .fml container — structure, encryption pipeline, and algorithms

1. Overview

.fml files are encrypted, compressed data containers produced by the MFME application. Each file contains one or more zlib-compressed data chunks, individually encrypted with a custom AES-based scheme. The decryption password is not stored directly; instead, a 4-byte seed at the end of the file is passed through a reversible Mixer function to derive an 8-character hex password.

last4 bytes → Mixer (100×) → 8-char hex password → RIPEMD-128 → 16-byte AES key → IV (AES-ECB of 0xFF×16) → ECL Decrypt → zlib Decompress → Plaintext
Key insight: The entire security depends on the secrecy of the Mixer algorithm and the hardcoded constant 0x00C59A00. Given the 4-byte seed, the password is fully deterministic. Two possible passwords are tried per file: the Mixer-derived one and a fallback b67de657.

2.2 Single-Chunk Files

Smaller .fml files contain exactly one payload chunk.

Offset Size Description ───────────────────────────────────────────────────────── 0x00 128 File header (see above) 0x80 4 csize — compressed/encrypted data size (uint32 LE) 0x84 4 dsize — decompressed data size (uint32 LE) 0x88 4 chunk_crc32 — CRC32 of decompressed chunk (init=0, no final XOR) 0x8C 4 next_header_offset — points to next chunk header (or last4 seed) 0x90 csize Encrypted zlib payload -4 4 last4 — password seed (uint32 LE)

2.3 Multi-Chunk Files

Larger files are split into multiple independently-encrypted chunks. Each chunk has its own 16-byte header and encrypted payload. All chunks share the same AES key and IV; ECL mode resets per chunk.

3. Format Phases (Phase 1 / Phase 2)

Two generations of .fml files exist, reflecting the development history of the original features:

PhasePasswordFile LayoutDetection
Phase 1 (legacy) Static key b67de657 Ends at EOF — no trailing seed Last chunk next_header_offset == file_size
Phase 2 (current) Seed-derived via Mixer 4-byte seed appended at EOF Last chunk next_header_offset == file_size - 4

The decoder walks the chunk header chain from offset 128, following each chunk's next_header_offset, and compares the final value to the file length to determine the phase automatically.

4. Decryption Pipeline (Step by Step)

4.1 Step 1 — Phase Detection

Walk the chunk header chain using next_header_offset to find the last chunk's header. If next_header_offset == file_size, the file is Phase 1 (legacy, static password b67de657). If next_header_offset == file_size - 4, the file is Phase 2 (4-byte seed present at EOF).

4.2 Step 2 — Extract last4 (Phase 2 only)

Read the final 4 bytes of the .fml file and interpret as a little-endian uint32. This is the password seed.

3.2 Step 2 — Mixer: Derive Password

Run the Mix() function for 100 iterations on the seed to produce the password. The output is an 8-character lowercase hex string (e.g. "01279247"). 

uint32 Mix(uint32 seed) {
    const uint32 ADDR = 0x00C59A00;
    uint32 v = seed;
    for (int i = 0; i < 100; i++) {
        uint32 x = ADDR ^ v;                          // XOR with constant
        uint32 v4 = (x >> 24) | (x << 24) | (x & 0x00FFFF00);  // byte swap end bytes
        v = (v4 << 3) | (v4 >> 29);                     // rotate left by 3
    }
    return v;
}

The Mixer is reversible — running Mix on the password yields the seed and vice versa (100 iterations each way).

3.3 Step 3 — RIPEMD-128: Derive AES Key

The 8-character ASCII password string is hashed with RIPEMD-128 to produce a 16-byte AES key. 

byte[] aesKey = Ripemd128.ComputeHash(Encoding.ASCII.GetBytes("01279247"));
// → 0e751ef3533305c26ac67b1a39204ac8

RIPEMD-128 uses Merkle–Damgård construction with 64 rounds. Four 32-bit state words (h₀–h₃) with parallel left/right lines that cross-feed into the final state. The algorithm pads the input to a multiple of 64 bytes (512 bits), appending 0x80, zero bytes, and an 8-byte little-endian message length in bits.

3.4 Step 4 — Derive IV

Encrypt a 16-byte block of all 0xFF with AES-128-ECB using the derived key. The result is the 16-byte initialization vector for ECL mode. 

byte[] iv = AES_ECB_Encrypt(aesKey, new byte[16] { 0xFF, 0xFF, ..., 0xFF });

3.5 Step 5 — ECL Decrypt (Custom Feedback Mode)

ECL is a custom AES-based stream/feedback mode designed for this format. It operates similarly to a two-register CFB variant. For each 16-byte block:

Full blocks (16-byte aligned)

  1. XOR the ciphertext block with the current feedback register fb_d → fb_b
  2. AES-ECB decrypt the original ciphertext block → dec
  3. XOR dec with fb_d → plaintext output
  4. Swap the feedback registers: fb_d ↔ fb_b
┌──────────┐ ┌──────────┐ ┌──────────┐ │ fb_d[i] │────▶│ XOR │────▶│ fb_b[i] │ (stored, not output) └──────────┘ └──────────┘ └──────────┘ ▲ │ ct[block] ┌────┴─────┐ │ AES-ECB │ ──▶ dec[block] │ DECRYPT │ └──────────┘ │ ┌────┴─────┐ │ XOR │ ◀── fb_d[i] └────┬─────┘ │ ▼ plaintext[block] After each block: SWAP(fb_d, fb_b)

Partial trailing block

For leftover bytes (fewer than 16), AES-ECB encrypt fb_d to produce a keystream, then XOR that keystream with the remaining ciphertext.

ECL encryption (forward direction)

The encrypt direction works symmetrically:

  1. XOR plaintext block with fb_d → AES input
  2. AES-ECB encrypt → ciphertext output
  3. XOR ciphertext with fb_d → fb_b
  4. Swap fb_d ↔ fb_b
Important: ECL state resets for each chunk. The IV is re-initialized to the same AES_ECB_Encrypt(key, 0xFF×16) value at the start of every chunk. Multi-chunk files are therefore decryptable independently of chunk order.

3.6 Step 6 — zlib Decompress

ECL output is raw zlib (RFC 1950) compressed data. Decompress with any standard zlib implementation (DEFLATE, RFC 1951, wrapped in zlib header/trailer).

3.7 Step 7 — Trim & Concatenate

Each chunk's decompressed output is trimmed to the exact dsize declared in its header (in case decompression produces extra bytes). All chunk outputs are concatenated in order to form the final plaintext.

5. ECL Mode — Detailed Algorithm

Pseudocode: Decrypt

ECL_Decrypt(ciphertext, aesKey, iv):
    fb_d = iv.copy()       // 16-byte feedback register D
    fb_b = new byte[16]    // 16-byte feedback register B
    result = new byte[ciphertext.Length]

    for each 16-byte block in ciphertext (except last partial):
        // Step 1: XOR ciphertext with fb_d → fb_b
        fb_b[j] = ciphertext[i+j] XOR fb_d[j]

        // Step 2: AES-ECB decrypt the ciphertext block
        dec = AES_ECB_Decrypt(aesKey, ciphertext[i .. i+15])

        // Step 3: XOR decrypted with fb_d → plaintext
        result[i+j] = dec[j] XOR fb_d[j]

        // Step 4: Swap feedback registers
        swap(fb_d, fb_b)

    // Handle partial trailing block (if any)
    if ciphertext has remainder R < 16:
        keystream = AES_ECB_Encrypt(aesKey, fb_d)
        for j in 0..R-1:
            result[fullBlocks + j] = ciphertext[fullBlocks + j] XOR keystream[j]

    return result

Pseudocode: Encrypt

ECL_Encrypt(plaintext, aesKey, iv):
    fb_d = iv.copy()
    fb_b = new byte[16]
    result = new byte[plaintext.Length]

    for each 16-byte block in plaintext (except last partial):
        // Step 1: XOR plaintext with fb_d → AES input
        block[j] = plaintext[i+j] XOR fb_d[j]

        // Step 2: AES-ECB encrypt
        ct[j] = AES_ECB_Encrypt(aesKey, block)[j]

        // Step 3: Ciphertext is output
        result[i+j] = ct[j]

        // Step 4: fb_b = ct XOR fb_d
        fb_b[j] = ct[j] XOR fb_d[j]

        // Step 5: Swap
        swap(fb_d, fb_b)

    // Handle partial trailing block
    if plaintext has remainder R < 16:
        keystream = AES_ECB_Encrypt(aesKey, fb_d)
        for j in 0..R-1:
            result[fullBlocks + j] = plaintext[fullBlocks + j] XOR keystream[j]

    return result

6. Cryptographic Primitives

5.1 AES-128-ECB

Used in two roles:

  • IV derivation: One-block encrypt of 0xFF × 16
  • ECL core: One-block encrypt/decrypt per 16-byte segment

No padding is used; all operations are on exactly 16-byte blocks.

5.3 zlib (RFC 1950)

Standard DEFLATE-compressed data wrapped in a 2-byte zlib header (CMF + FLG) and a 4-byte Adler-32 trailer. The first byte is typically 0x78 (deflate, 32K window).

9. Implementation Notes

Decryption flow in C#

// 1. Read the .fml file
byte[] fml = File.ReadAllBytes("sample.fml");

// 2. Extract seed (last 4 bytes)
uint seed = BitConverter.ToUInt32(fml, fml.Length - 4);

// 3. Derive password via Mixer (100 iterations)
uint passwordNum = Mix(seed);
string password = passwordNum.ToString("x8");  // 8-char hex

// 4. Hash password → AES key
byte[] aesKey = Ripemd128.ComputeHash(Encoding.ASCII.GetBytes(password));

// 5. Derive IV
byte[] iv = AES_ECB_Encrypt(aesKey, new byte[16] { 0xFF, ..., 0xFF });

// 6. For each chunk: ECL decrypt → zlib decompress → trim to dsize
foreach chunk:
    byte[] compressed = EclDecrypt(chunk_ct, aesKey, iv);
    byte[] plaintext  = ZlibDecompress(compressed);
    plaintext = plaintext[0 .. chunk.dsize];
    output.Append(plaintext);

Fallback password

If primary decryption (Mixer-derived password) fails, a hardcoded fallback "b67de657" is attempted. This covers edge cases where files use a fixed password rather than the Mixer-derived scheme.

Minimal file size

A valid .fml must be at least 148 bytes: 128 (header) + 16 (chunk 1 header) + 4 (last4). This implies a minimum encrypted payload of at least 0 bytes (header-only chunk).
